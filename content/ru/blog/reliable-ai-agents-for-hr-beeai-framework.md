Создание AI-агента, который отлично работает в тестах — это только половина дела. Настоящие проблемы начинаются в продакшене: агент может пропустить этап валидации данных, преждевременно закончить диалог или начать использовать инструменты в неверном порядке. В сфере HR, где важна последовательность (от проверки подписки на уведомления до сбора зарплатных ожиданий), такая непредсказуемость недопустима.

В этой статье мы разберем, как построили HR-систему на базе **BeeAI Framework** и почему перешли от сложных графов к декларативным требованиям **RequirementAgent**.

## Архитектура и технологический стек

Наше решение объединяет гибкость Python для AI-логики и надежность TypeScript для системных сервисов:

* **Клиент (Telegram):** Используется библиотека **GramJS**. Она позволяет реализовать полноценное клиентское приложение (UserBot), которое может управлять диалогами, обрабатывать события и форматировать сообщения. 


* **Протокол инструментов (MCP):** Мы использовали **Model Context Protocol** для стандартизации доступа к бизнес-логике. Инструменты (поиск вакансий, сохранение резюме) реализованы на TypeScript, но легко подключаются к Python-агенту через MCP-клиент. 


* **Оркестрация (Python BeeAI):** Основной "мозг" системы. Мы используем **RequirementAgent** для управления логикой диалога. 


* **Рабочие процессы (Temporal):** Для управления долгоживущими диалогами и обеспечения отказоустойчивости (например, если пользователь ответил через 2 дня).

## Почему RequirementAgent?

Основная проблема фреймворков вроде **LangGraph** или **LangChain** при создании сложных агентов — это необходимость вручную описывать каждый узел графа и логику переходов. Это приводит к раздутому коду (150+ строк для простого сценария) и сложности в поддержке.

**RequirementAgent** в BeeAI решает это через систему **декларативных требований**. Вместо того чтобы рисовать стрелочки в графе, вы просто говорите агенту:

1. **Сначала обязательно "подумай"** (инструмент `ThinkTool`).
2. **Используй инструмент скрининга только ПОСЛЕ** получения резюме.
3. **Не спрашивай зарплату дважды** подряд.

### Сравнение с LangGraph

| Особенность | LangGraph / LangChain | BeeAI RequirementAgent |
| --- | --- | --- |
| **Логика управления** | Явные узлы и ребра (Imperative) | Правила и ограничения (Declarative) |
| **Объем кода** | Высокий (нужно описывать состояние и роутинг) | Низкий (около 30-40 строк на агента) |
| **Надежность** | Зависит от точности описания графа | Гарантируется фреймворком через валидацию шагов |
| **Гибкость** | Жесткая структура | Агент сам ищет путь, соблюдая правила |

## Реализация решения: Примеры кода

### 1. Подключение инструментов через MCP

В нашей системе инструменты для работы с вакансиями (написанные на TS) пробрасываются в Python-агент за несколько строк:

```python
from beeai_framework.tools.mcp import MCPTool
from src.utils.http_client import streamablehttp_client

async def get_hr_tools():
    # Подключаемся к MCP серверу, который экспортирует HR инструменты
    mcp_url = "http://mcp-server:3001"
    client = streamablehttp_client(mcp_url)
    all_tools = await MCPTool.from_client(client)
    return all_tools
```



### 2. Описание HR-агента с RequirementAgent

Здесь мы задаем правила игры: агент обязан использовать `ThinkTool` на первом шаге и соблюдать последовательность инструментов.

```python
from beeai_framework.agents.experimental import RequirementAgent
from beeai_framework.agents.experimental.requirements.conditional import ConditionalRequirement
from beeai_framework.tools.think import ThinkTool

agent = RequirementAgent(
    llm=llm,
    tools=[ThinkTool(), get_resume_tool, get_offers_tool],
    instructions="Вы — HR-рекрутер. Ваша цель: провести скрининг кандидата.",
    requirements=[
        # Обязательно "подумать" перед ответом на первом шаге
        ConditionalRequirement(ThinkTool, force_at_step=1),
        # Искать офферы только после получения контекста резюме
        ConditionalRequirement(get_offers_tool, only_after=[get_resume_tool], min_invocations=1),
    ],
    memory=memory
)
```

## Как это работает в HR-сценарии

В нашем проекте агент проходит через несколько критических стадий, которые контролируются промптами и правилами `RequirementAgent`: 

1. **Проверка подписки:** Агент использует `NotificationsSubscribeTool`, чтобы убедиться, что кандидат готов получать уведомления. 


2. **Анализ резюме:** С помощью `GetSpecialistResumeTool` извлекаются навыки. 


3. **Мэтчинг вакансий:** Агент показывает подходящие варианты через `GetActiveOffersTool`. 


4. **Сбор требований:** Если кандидат заинтересован, агент переходит к уточнению зарплаты и даты выхода. 

**RequirementAgent** гарантирует, что агент не перепрыгнет к предложению вакансии, не узнав сначала, какие навыки есть у специалиста. Если LLM попытается это сделать, фреймворк заблокирует вызов инструмента и заставит агента следовать правилу `only_after`.

## Какие продакшен-баги мы получили и как BeeAI помог их устранить

До внедрения BeeAI наш HR-агент представлял собой связку **LLM + системный промпт + история сообщений**. Сценарий был подробно описан, но на практике это означало, что корректность диалога целиком зависела от того, *как модель интерпретирует текст переписки*. В продакшене это привело к ряду повторяющихся ошибок.

Ниже — несколько характерных примеров.

---

### Баг 1. Агент нарушал порядок этапов диалога

**Симптомы**

* агент переходил к обсуждению вакансии без явного согласия кандидата;
* мог запросить ФИО или резюме до обсуждения условий;
* «перепрыгивал» этапы при нестандартных ответах.

Причина была простой:
**единственный контекст агента — история сообщений**, без явного знания:

* получено ли согласие;
* выбрана ли вакансия;
* завершён ли предыдущий шаг.

---

**Как это было решено**

В BeeAI мы зафиксировали порядок шагов в виде декларативных требований:

```python
requirements=[
    # Нельзя работать с вакансиями без согласия кандидата
    ConditionalRequirement(
        NotificationsSubscribeTool,
        min_invocations=1
    ),

    # Показывать вакансии можно только после согласия
    ConditionalRequirement(
        GetActiveOffersTool,
        only_after=[NotificationsSubscribeTool]
    ),

    # Запрашивать резюме — только после выбора вакансии
    ConditionalRequirement(
        SendResumeTool,
        only_after=[GetActiveOffersTool]
    ),
]
```

Теперь, даже если LLM «решает», что пора перейти к следующему шагу,
**фреймворк блокирует вызов инструмента**, пока не выполнены условия.

В результате агент перестал нарушать последовательность, независимо от формулировок ответов кандидата.

---

### Баг 2. Повторные контакты игнорировали прошлые отказы

**Симптомы**

* кандидат отказался от аутстаффа;
* спустя время агент снова писал ему;
* иногда — с предложением по другой специальности.

Хотя история переписки сохранялась, отказ существовал **только как текст**, а не как бизнес-факт.

---

**Как это было решено**

Отказы и согласия были вынесены в **явное состояние**, фиксируемое инструментами и сохраняемое в памяти агента:

```python
class DeclineSubscriptionTool(Tool):
    async def run(self):
        memory.set("subscription_declined", True)
```

И далее это состояние используется в требованиях:

```python
ConditionalRequirement(
    GetActiveOffersTool,
    forbidden_if=["subscription_declined"]
)
```

Теперь агент:

* не может отправлять вакансии при активном отказе;
* учитывает TTL (например, 90 дней);
* не зависит от длины или формата истории диалога.

---

### Баг 3. Агент отвечал «не на ту вакансию»

**Симптомы**

Кандидат отвечал по конкретной вакансии,
но агент формировал ответ или уведомление с **другим ID вакансии**.

Это происходило, когда в истории диалога фигурировало несколько предложений, и LLM выбирал «похожее» по смыслу.

---

**Как это было решено**

Мы ввели обязательную фиксацию выбранной вакансии:

```python
ConditionalRequirement(
    SendResumeTool,
    only_after=[SelectVacancyTool]
)
```

`SelectVacancyTool` сохраняет `vacancy_id` в памяти, и все дальнейшие шаги обязаны ссылаться именно на него.

Таким образом:

* контекст вакансии стал явным;
* агент больше не «угадывает», о чём идёт речь;
* ответы и действия жёстко привязаны к выбранному предложению.

---

### Баг 4. Утечка внутренней информации кандидату

**Симптомы**

В отдельных сообщениях кандидатам уходили:

* ставки закупки;
* внутренние комментарии;
* данные, предназначенные для рекрутеров.

Причина — LLM получал единое описание вакансии без чёткого разделения ролей.

---

**Как это было решено**

Мы разделили доступ к данным на уровне инструментов:

* `GetVacancyForCandidateTool`
* `GetVacancyInternalTool`

И запретили использование internal-инструментов в пользовательском контуре:

```python
ConditionalRequirement(
    GetVacancyInternalTool,
    forbidden_in_user_messages=True
)
```

Даже если модель «знает» эти данные, она **не может использовать соответствующий инструмент** в диалоге с кандидатом.

---

### Баг 5. Агент «молчал» или не формировал черновик ответа

**Симптомы**

* сообщение не формируется;
* черновик пуст;
* отсутствует сигнал об ошибке.

---

**Как это было решено**

Каждый диалог был оформлен как **долгоживущий workflow в Temporal**:

* если агент не может выполнить требования — возникает ошибка;
* workflow делает retry или уходит в failed-state;
* система отправляет уведомление об ошибке.

Таким образом, сбой LLM больше не означает «потерянный диалог».

---

## Что изменилось принципиально

До внедрения BeeAI агент полагался на «разумность» LLM и длину истории сообщений.
После — поведение агента стало **ограничено формальными правилами**, проверяемыми на каждом шаге.

Мы перестали ожидать, что модель *сама* будет соблюдать сценарий,
и начали **принуждать её к корректному поведению на уровне исполнения**.


* Никогда не забывает про конфиденциальность клиента (строго следует системному промпту). 


* Всегда обращается к кандидату на "Вы". 


* Гарантированно выполняет все шаги HR-скрининга в правильном порядке.

Это делает AI-агента по-настоящему готовым к работе с реальными людьми в критически важных бизнес-процессах.
